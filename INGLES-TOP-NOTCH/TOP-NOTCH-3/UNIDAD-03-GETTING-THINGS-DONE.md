## 1. 🎯 Objetivos

- Pedir, delegar y hacer seguimiento de tareas con precisión.
- Contratar servicios y comunicar expectativas claramente.
- Usar el causativo avanzado y el infinitivo perfecto.
- Expresar que algo debería haberse hecho (crítica a acciones pasadas).

---

## 2. 🧠 Gramática principal: Should have / Could have / Would have + PP (Crítica y arrepentimiento)

### ¿Por qué aquí?

Cuando delegas tareas y las cosas no salen bien — o mejor de lo esperado — necesitas expresar lo que debería haberse hecho diferente. Estas estructuras son esenciales en comunicación profesional y gestión de proyectos.

---

### Estructura

```
Modal + have + past participle
```

| Modal | Significado | Ejemplo |
|---|---|---|
| **should have + PP** | debería haber hecho (pero no se hizo) | You **should have** called before coming. |
| **shouldn't have + PP** | no debería haber hecho (pero se hizo) | I **shouldn't have** waited so long. |
| **could have + PP** | podría haber hecho (era posible, no se hizo) | She **could have** finished it yesterday. |
| **couldn't have + PP** | no habría podido (imposible) | We **couldn't have** known this would happen. |
| **would have + PP** | habría hecho (condicional pasado irreal) | He **would have** helped if he'd known. |
| **might have + PP** | podría haber (posibilidad pasada) | She **might have** misunderstood the brief. |
| **needn't have + PP** | no era necesario (pero se hizo igual) | You **needn't have** printed the whole document. |

---

### En contexto de trabajo y delegación

| Situación | Expresión |
|---|---|
| Tarea no entregada | You should have sent this on Friday. |
| Error que pudo evitarse | This bug could have been caught in review. |
| Esfuerzo innecesario | You needn't have redone the whole design. |
| Disculpa profesional | I should have communicated this earlier. |
| Expectativa no cumplida | The contractor should have finished by now. |

## 4. 🔗 Collocations clave

| Collocation | Traducción | Ejemplo |
|---|---|---|
| **meet** a deadline | cumplir una fecha límite | We need to meet the Friday deadline. |
| **miss** a deadline | incumplir una fecha límite | The contractor missed the deadline by three days. |
| **get** something **done** | hacer que algo se haga | I need to get this sorted before tomorrow. |
| **have** something **done** | mandar hacer algo | We had the server upgraded last week. |
| **take care of** something | encargarse de algo | Can you take care of the invoicing? |
| **put off** a task | aplazar una tarea | Don't put off what you can do today. |
| **run behind** schedule | ir atrasado | The project is running behind schedule. |

## 5. 🗣️ Casos de uso reales

### Caso 1 — Delegando tareas en un standup de equipo

> **Situación:** El tech lead del equipo de RIWI organiza las tareas del sprint en el standup del lunes.

```
Lead:     Good morning everyone. Quick standup — let's go around.
           Carlos, where are you with the auth module?

Carlos:   I finished the login flow on Friday. 
           I should have pushed the PR earlier, but I was waiting 
           on Valentina's component. It's up now.

Lead:     Got it. Valentina?

Valentina: My component is done and merged. 
            I could have finished it Thursday, 
            but the design specs changed last minute.

Lead:     Noted — that spec change should have been communicated earlier.
           Diego, what about the API integration?

Diego:    Still in progress. I'm running into some CORS issues.
          I might have needed to escalate this earlier, honestly —
          I've been stuck on it since Friday.

Lead:     Okay — you should have looped in the backend team.
           Let's do that right now. Can you ping Andrés after this?

Diego:    Already done — just sent him a message.

Lead:     Good. Ana, the test coverage?

Ana:      I've set up the test structure, but I needn't have 
          written all the mocks from scratch — 
          I found a utility library halfway through.

Lead:     Ha — that happens. Is it all working now?

Ana:      Yes, 92% coverage on the main modules.

Lead:     Great. Main blocker is Diego's CORS issue — 
           everything else is on track. Let's check in this afternoon.
```

**Nota gramatical:** `I should have pushed the PR earlier`, `That spec change should have been communicated`, `You should have looped in`, `I might have needed to escalate`, `I needn't have written all the mocks` — modal + have + PP naturalmente distribuidos en un standup real.

### Caso 2 — Email de seguimiento a un contratista

> **Situación:** Carlos escribe a un freelancer de diseño que no ha entregado a tiempo.

```
Subject: Follow-up — Landing Page Design — Missed Deadline

Hi Marco,

I'm writing to follow up on the landing page designs.
As discussed in our agreement, the first mockups were due last Wednesday.
We are now five days past that deadline with no delivery.

I should have followed up sooner — I assumed there would be a message 
from you if there were any issues. That's on me.

However, I need to be direct: you should have communicated any delays 
before the deadline, not after. The team was counting on these assets 
to begin development this week.

Could you let us know:
1. Where you currently stand with the deliverables.
2. A realistic new delivery date.
3. Whether there were any blockers we could have helped resolve.

If the revised date is not met, we may need to discuss the penalty clause 
in our agreement. We would like to avoid that, of course.

Please respond today if possible.

Best,
Carlos Moreno
Project Lead — RIWI Capstone Team
```

**Nota gramatical:** `I should have followed up sooner`, `you should have communicated`, `blockers we could have helped resolve` — uso del modal perfecto para señalar responsabilidades sin ser agresivo.

### Caso 3 — Análisis post-proyecto (retrospectiva)

> **Situación:** El equipo de RIWI hace una retrospectiva al final del sprint. Identifican qué salió bien y qué podría haber salido mejor.

```
SPRINT RETROSPECTIVE — RIWI Frontend Team
Date: October 18, 2025

WHAT WENT WELL:
- Delivered 8 of 9 story points.
- Communication in Slack was consistent and documented.
- The demo was well-received by instructors.

WHAT COULD HAVE BEEN BETTER:

Technical:
- The API integration should have been tested earlier in staging.
  We caught issues only two days before demo — we could have 
  avoided that with earlier environment testing.
- The state management approach could have been simpler. 
  We overengineered the Redux setup — we should have 
  considered Zustand or Context API first.

Communication:
- The design specs changed twice without formal notice.
  This shouldn't have happened without team sign-off.
  We should have required written confirmation for any changes.
- Diego's CORS issue sat unresolved for two days longer than needed.
  He should have escalated it sooner, and we should have 
  checked in more proactively.

Process:
- We could have used the PR review process more consistently.
  Two PRs were merged without review — that shouldn't have happened.

ACTION ITEMS FOR NEXT SPRINT:
1. All spec changes require written approval before implementation.
2. Any blocker unresolved after 4 hours must be escalated.
3. No PR merges without at least one review.
```

### Caso 4 — Guía de gestión personal de tareas (artículo)

> **Situación:** Artículo del blog de RIWI sobre productividad para desarrolladores.

```
Why Developers Procrastinate (And What to Do About It)

Most developers I know are excellent at solving complex technical problems.
They're terrible at replying to emails.

This isn't laziness. It's a version of what psychologists call 
"task avoidance" — we put off things that feel ambiguous or unpleasant 
in favor of things that feel productive, even when those things 
are less important.

I should have submitted this article last week, by the way.
I've been debugging a CSS issue instead. Classic.

THE PATTERNS:

1. You should have started earlier, but you didn't.
   The fix: start before you're ready. 
   The first 10 minutes of any task are the worst.
   After that, momentum takes over.

2. You're waiting for perfect conditions.
   There are no perfect conditions. The design spec will change.
   The requirements will shift. Ship something that works,
   then iterate. You could have shipped v1 two weeks ago
   if you'd let go of the fantasy of a perfect v1.

3. You've taken on too much.
   You should have said no to at least one of those commitments.
   Learn to protect your bandwidth. No is a complete sentence.

4. You're doing low-effort tasks to feel productive.
   Organizing your file structure for the fourth time this week 
   isn't work. You know what the real task is. 
   You needn't have reorganized anything — 
   you needed to write the function.

The good news: awareness is the first step. 
The bad news: you've known this for a while and you've been putting 
off doing anything about it. Which is, in a way, the whole point.
```

## 6. ⏱️ Modal + Have + PP en distintos contextos

| Uso | Ejemplo |
|---|---|
| Crítica (algo que debió hacerse) | You should have tested it first. |
| Arrepentimiento | I shouldn't have agreed to that timeline. |
| Posibilidad no realizada | We could have delivered this yesterday. |
| Imposibilidad pasada | They couldn't have known about the change. |
| Esfuerzo innecesario | You needn't have rewritten the entire module. |
| Pasiva modal perfecta | This bug should have been caught in review. |

---

## 7. ⚠️ Errores frecuentes

### `Should have` sin participio pasado

❌ You should have call me.
✅ You should have **called** me.

### Confundir `should have` con `should`

- `You **should** test it.` → consejo para el futuro/presente
- `You **should have** tested it.` → crítica al pasado (ya no puedes)

### `Needn't have` vs `didn't need to`

- `You **needn't have** printed it.` → lo hiciste, pero no era necesario
- `You **didn't need to** print it.` → no era necesario (y probablemente no lo hiciste)
